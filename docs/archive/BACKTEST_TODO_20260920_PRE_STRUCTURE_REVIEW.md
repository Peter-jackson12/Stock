기준일: 2026-09-19. 목표는 **검증 가능한 실제 입력 하나로 원본 틱 → 신호 → 주문 → 체결 → 결과를 대조**하는 것이다.
전략 수익성 입증과 실거래 운영 승인은 별도 단계다. 원본 틱 재생이 주 경로이며 LOB/초봉 변환은 필요하지 않다.

### 2026-09-20 방향 결정 — `cf18cb43…` 100건 표본을 다음 필수 단계에서 제외, clean 세션 우선

**`cf18cb43…`에 대한 `inspect_raw_v2_sample.py --start-seq 1 --limit 100`을 더 이상 무조건적인
다음 실행으로 유지하지 않는다.** 이번에 `engine/tick_research_run.py::run_raw_v2()`와
`scripts/inspect_raw_v2_sample.py`/`TICK_RESEARCH_RUNBOOK.md#닫힌-raw의-제한된-표본-대조`의
현재 코드 계약만 다시 읽었다(재실행 없음). 이 표본 검사가 확인할 수 있는 것과 없는 것은 다음과 같다.

- **확인할 수 있는 것:** 저장 당시 envelope에 실제로 기록된 `price_policy`/`direction_policy`
  그대로를 `normalize_tick()`에 재입력했을 때, 저장된 정규화 이벤트·품질 기록과 재계산 결과가
  일치하는지(`sample_consistent`)뿐이다. 즉 "그 파일이 **당시 자신의 정책** 기준으로 내부
  일관적인가"만 확인한다.
- **확인할 수 없는 것:** `cf18cb43…`는 `direction_policy="unknown"`으로 저장됐으므로, 이 표본이
  `sample_consistent`로 나와도 그것은 "unknown 정책 재적용 결과가 저장값과 같다"는 뜻일 뿐,
  **현재 기본 정책인 `signed_volume` 기준의 연구 적합성을 전혀 검증하지 않는다.**
  `inspect_raw_v2_sample.py`는 최신 기본 정책을 과거 파일에 강제 적용하지 않고, 원본 envelope의
  정책을 그대로 되돌려 쓰는 도구이기 때문이다(런북에 이미 명시: "원문에 저장된 가격·방향 정책을
  그대로 사용한다. 정책 누락/오류를 최신 기본값으로 채우지 않는다").
- 또한 코드 0(`sample_consistent`)이어도 런북이 명시한 대로 `full_integrity_verified=false`,
  `feed_accuracy_verified=false`, `replay_performed=false`이며 **연구 입력 합격이 아니다.**
  표본 밖 구간·전체 무결성·`run_raw_v2()`의 엄격 whole-file 계약 통과 여부는 별도다.

따라서 `cf18cb43…`의 100건 표본 검사는, 통과하더라도 "이 파일이 signed_volume 기준
연구에 쓸 수 있다"는 근거를 만들지 못한다. 이미 알려진 방향 정책 불일치(8.6%, 제어 레코드
99.8% 소멸)를 뒤집을 수 있는 검사가 아니므로, 이 검사를 우선 실행할 이유가 약하다.
이번 작업에서는 이 검사를 실행하지 않았다.

현재 확보된 실제 raw v2 파일 5개 중 현행 엄격 `run_raw_v2()` 계약을 그대로 통과한다고

### 다음 최소 실제 관측 (경로 A, 이번에는 실행하지 않음 — 계획만)

다음 시장 세션에서 현재 코드로 정규장 수집을 실행한 뒤, 다음 항목부터 저장 종료 근거로 대조한다.
수집 실행 자체와 로그인·구독·예약은 이번 작업에서 하지 않았고, 이 목록은 사용자 승인 후
실제 수집을 실행할 때 확인할 항목이다.

- 실행 전 코드 revision(수집 시작 직전 `git rev-parse HEAD`).
- `direction_policy`(현재 기본값이 `signed_volume`인지 코드로 재확인) / `price_policy`.
- `feed_scope`(전 종목 구독 여부, venue 확정 여부).
- 신규 세션의 `session_id`.
- 수집 시작/종료 근거: `capture_status.json`·세션 `status.json`의 state/accepting/writer_closed/
  finalization/error/dropped, peer 종료 보고, 로그 말미.
- `writer_closed=true` 및 `finalization` 존재 여부.
- accepted=committed 콜백 건수와 final_seq 일치 여부, 오류·드롭 0 여부.
- 종료 프로세스(본체·실행기·로그 감시) OS 부재 대조.
- 파일 크기·`LastWriteTimeUtc`.

이 관측이 모두 정상이면, 그다음에야 제한 표본 대조(`inspect_raw_v2_sample.py`, 시작/중간/말미
각 300건 수준)와 CaptureControl 품질 제어 기록(session_start/session_note 외 존재 여부)을
확인한다. 전체 무결성 검사는 그 이후 별도 장외 단계다. 이번 작업에서는 이 중 어느 것도 실행하지 않았다.

## 3. 장외 실행 전 준비

- [ ] **실행 계획 확정:** 대상·장외 시간·허용 I/O/시간·중단 기준·출력 위치·여유 공간을 정한다.
  수집과 겹치지 않게 하고 최신 종료 상태를 대조한다. 이 체크리스트 작성은 실제 실행 지시가 아니다.
- [ ] **실행 경로 선택:** 화면의 32 MiB·100,000 raw 상한 안인지 확인한다.
  초과 파일은 명시적 CLI 계획이 필요하다. 종목 하나를 골라도 전체 입력을 읽으므로 부하가 작다고 가정하지 않는다.
- [ ] **입력 전체 검증:** 승인된 장외 범위에서 전체 순번·체크섬·품질 계약을 검사하고 근거를 보존한다.
  실패하면 연구 입력 합격으로 처리하지 않는다. 기존 300건 표본이나 저장 종료 확인으로 대체하지 않는다.

## 4. 첫 시험 실행과 결과 대조

- [ ] **시험 실행 1회:** 확정된 입력·설정·코드 버전으로 실행하고 입력 출처와 결과 경로를 남긴다.
- [ ] **결과 상태 확인:** 전체 입력 처리 여부·오류·체결 없음·미청산을 구분한다.
  failed 결과의 중간 수익을 정상 성과로 해석하지 않는다.
- [ ] **대표 사례 수동 대조:** 원본 이벤트부터 신호·주문·체결 가격/수량까지 연결해 확인한다.
  진입 사례가 없다면 원인을 기록하고, 체결 경로의 실데이터 검증은 미완료로 남긴다.
- [ ] **재현성 대조:** 같은 입력·설정·코드의 재실행에서 주문·체결·경제적 결과가 같은지 확인한다.
  실행 ID·생성 시각처럼 달라져야 하는 메타데이터는 비교에서 구분한다. 재실행도 장외 I/O 계획에 포함한다.
- [ ] **첫 시험 종료 기록:** 성공/실패 원인, 확인한 범위와 남은 한계를 HANDOFF에 남긴다.
  위 항목의 근거가 있어야 시험 완료로 표시한다. 전략 수익성 확인으로 확대하지 않는다.

## 5. 첫 시험 이후 — 전략 평가

- [ ] 여러 날짜·시장 상황·종목에서 품질이 확인된 입력과 전략 진입 사례를 축적한다.
- [ ] 학습/조정에 쓴 구간과 평가 구간을 분리하고, 비용·지연·체결 가정 변화에 따른 결과를 비교한다.
- [ ] 손익뿐 아니라 거래 수·손실 구간·미체결·미청산·데이터 제외 내역을 함께 검토한다.
  필요한 데이터 기간은 거래 빈도와 평가 목적에 맞춰 정하며 현재 용량만으로 충분성을 선언하지 않는다.
